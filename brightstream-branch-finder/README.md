# BrightStream Branch Finder

BrightStream Branch Finder is a reusable integration module for the BrightStream Bank website. It helps users find branches in two ways:

- By current location: detects the user position and returns the nearest branch.
- By city search: shows all branches available in a selected city.

In both flows, users get an interactive map view and quick access to Google Maps directions.

## Live Demo

- https://brightstream-branch-finder-liard.vercel.app/

## What This Module Does

- Finds the nearest branch using browser geolocation.
- Calculates branch distance with the Haversine formula.
- Supports city-based branch lookup from preloaded branch data.
- Renders map visualization with Leaflet and marker clustering.
- Highlights nearest branch and user location on the map.
- Includes "Get Directions" links that open Google Maps.
- Caches branch data in `localStorage` (24-hour TTL) to reduce repeated fetches.

## Environment Variables

Create a `.env` file in `brightstream-branch-finder/` with:

```env
OPTIMIZELY_GRAPH_URL=https://cg.optimizely.com/content/v2
OPTIMIZELY_GRAPH_KEY=your_optimizely_graph_api_key
```

Variable reference:

- `OPTIMIZELY_GRAPH_URL`: Base URL for Optimizely Graph API.
- `OPTIMIZELY_GRAPH_KEY`: API key used by the backend/API layer to query branch data.

Optional/local platform variable:

- `.env.local` may include `VERCEL_OIDC_TOKEN` generated by Vercel CLI. This is not required for core local development of the branch finder widget.

Security note:

- Do not commit real keys or tokens. If any secret was exposed in git history, rotate it.

## Data Flow Summary

1. Branch data is fetched via `POST /api/graph`.
2. Results are normalized and coordinates are parsed.
3. In nearest mode:
   - Browser geolocation retrieves user coordinates.
   - Distances are computed against all valid branches.
   - Closest branch is selected and highlighted.
4. In city mode:
   - User selects a city from suggestions.
   - Matching branches are displayed and centered on map.

## UX Behavior

- Initial load prefetches branch data to populate city suggestions.
- Nearest flow displays branch name, city/country, distance, and phone.
- Map popups include branch info and a Google Maps directions link.

## Brief Overview of My Approach

After receiving the task, I first explored the GraphQL API in Postman to understand the schema, types, and available data.

During this phase, I found data limitations in the response payload for fields such as direct `latitude`, `longitude`, and address details. The initial plan was to calculate the nearest branch directly from lat/lon plus browser geolocation, but due to the response limitations I decided to use the `Coordinates` field and parse/extract latitude and longitude from it.

I implemented this core nearest-branch logic first (without focusing on design) to validate the approach end-to-end.

Next, I hit another API constraint: I could not reliably apply a `where` query for server-side city filtering (likely due to access limitations). To keep the solution practical:

- I fetch up to 100 branch items (which appears to cover the dataset size for this task).
- I cache results in `localStorage`.
- I perform city filtering client-side from cached data.
- I also load city names to populate the city search dropdown.

Once the core data and filtering logic was stable, I focused on UI/UX improvements including map integration, responsive behavior, and user interaction polish.

## Integration Notes

This module is designed as a feature component that can be embedded into a larger BrightStream Bank website experience. It can be wired into existing page layouts and backend GraphQL/API gateways with minimal coupling.

## Known Limitations (Developer POV)

- During API schema investigation, latitude and longitude fields appeared to exist, but they were not reliably returned together with branch address and related fields in the query responses used by this module.
- This may indicate permission-restricted fields or that a different schema/view is being queried at runtime.
- I also could not reliably use a where query for server-side city filtering, likely due to API access/scope limitations.
- UI spacing and element heights are not fully pixel-perfect yet. The current implementation prioritizes functional completeness while maintaining the BrightStream visual aesthetic.

## Assumptions / Decisions Made

- Because direct latitude/longitude fields were not consistently available in fetched data, the module parses and extracts `lat`/`lon` values from the `Coordinates` field.
- Distance calculations and nearest-branch logic are based on these parsed coordinate values.
- Because server-side where filtering was not reliably available, the module fetches up to 100 branch records, caches them in localStorage, and performs city filtering client-side.
